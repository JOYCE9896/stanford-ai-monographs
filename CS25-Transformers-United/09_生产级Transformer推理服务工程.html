第九讲：生产级Transformer推理服务工程

训练好一个模型只是开始，让它以能承受的成本、稳定地回应成千上万个并发请求是另一门工程

主讲：Charles Frye（Modal）
对应真实材料：Modal《GPU Glossary》、《LLM Engineer's Almanac》推理性能基准报告

一、 背景知识：推理和训练面对的是不同的瓶颈

训练一个模型时，GPU 大部分时间在做大批量的矩阵乘法，这正是现代加速器最擅长、利用率最高的运算模式。推理，尤其是逐个生成 token 的自回归推理，情况不一样：每生成一个新 token，模型都要把全部参数从显存搬进计算核心走一遍前向计算，但每次只处理一个 token 的数据量，计算量相对搬运数据的开销来说很小。Frye 对这个现象的概括是，单条请求的逐 token 生成，容易被"反复搬运模型权重"这件事本身拖慢，而不是被算力上限拖慢。

这个瓶颈通常用"算术强度"（arithmetic intensity）来衡量，也就是每从显存读取一个字节的数据，能配上多少次浮点运算。矩阵乘法这类运算算术强度很高，GPU 能被充分喂饱。单条请求的逐 token 生成算术强度很低，大量时间花在等待数据搬运上，GPU 的计算单元实际处于闲置状态。

二、 KV Cache：避免每一步都重新计算整段历史

自回归生成时，模型在生成第 t 个 token 时，需要用注意力机制关注前面所有已经生成的 token。如果每生成一个新 token 都重新对全部历史文本做一遍完整的注意力计算，浪费会非常大，因为历史部分的 Key 和 Value 向量在每一步之间根本没有变化。KV Cache（键值缓存）的做法是把已经算过的 Key 和 Value 向量缓存下来，新生成一个 token 时只需要计算它自己的 Key、Value，并和缓存里已有的部分做注意力计算，不必重算历史。

KV Cache 带来的代价是显存占用：缓存的大小随对话轮数、上下文长度线性增长，长对话或者高并发场景下，光是存这些缓存就可能占用大量显存，这也是为什么"KV Cache 显存管理"本身发展成了一个独立的工程问题，业内针对它出现了各种压缩、淘汰、分层存储方案。

三、 用批处理把闲置的算力利用起来

既然单条请求的逐 token 生成算术强度低、GPU 容易闲置，一个自然的应对办法是让 GPU 同时处理多条请求的生成，让本来分散、零碎的计算凑到一起，重新变成 GPU 擅长的批量运算模式。但语言模型服务面对的请求长度千差万别，有的请求几个 token 就结束了，有的还要继续生成几百个 token，如果用最朴素的静态批处理，等一批请求里最长的那条生成完才能开始处理下一批，短请求会被拖累，GPU 也会有大量空闲时间。

连续批处理（continuous batching）是应对这个问题的常见做法：不再要求一批请求必须同进同出，而是每当有请求生成完毕腾出位置，立刻让新请求补进来，让 GPU 始终保持接近满载的状态运行。Frye 团队的基准测试工作，正是系统比较 vLLM、SGLang、TensorRT-LLM 这几类主流推理服务框架，在不同模型、不同上下文长度、不同数值精度下的吞吐量和首 token 延迟表现。

四、 更进一步的优化：投机采样与缓存压缩

投机采样（speculative sampling）是另一类思路：用一个小、快的草稿模型先一次性猜测生成接下来的若干个 token，再用真正要部署的大模型一次性对这些猜测做验证。如果草稿模型猜对的比例足够高，大模型每次验证多个 token 的成本，比逐个生成这些 token 的成本更低，因为验证过程可以像处理一批 token 一样并行计算，重新把算术强度提上去。

Frye 团队展示的另一类工作方向是对 KV Cache 本身做无损压缩，报告中提到的压缩比可以达到 4 倍，让同样的显存能撑更长的上下文或更多并发请求。这一讲把这些技术放在一起看，传递的核心信息是：一个模型从训练完成到能够以合理成本大规模对外提供服务，中间还有一整套独立的系统工程要做，而这套工程处理的瓶颈，和训练阶段面对的瓶颈往往不是同一类问题。
