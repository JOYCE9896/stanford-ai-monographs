第四讲：万卡集群训练与超大规模并行工程

一个模型太大，一块 GPU 装不下、也算不动的时候，工程上到底在切什么

主讲：Nouamane Tazi（Hugging Face）
对应真实材料：Hugging Face《The Ultra-Scale Playbook》，基于超过 4,000 次真实扩展实验、最多用到 512 块 GPU 的训练手册

一、 背景知识：为什么一块 GPU 不够用

训练一个语言模型，显存里要同时装下三样东西：模型参数本身、反向传播算出的梯度，以及优化器状态。如果用 Adam 优化器，还要为每个参数额外存两个统计量。用混合精度训练来算，参数和梯度用 16 位浮点存储，同时保留一份 32 位精度的参数副本和优化器状态用于稳定更新，一个有 N 个参数的模型，大致需要 2N（16 位参数）加 2N（16 位梯度）加 4N（32 位参数副本）加 8N（32 位 Adam 优化器状态），合计约 20N 字节的显存。

这个系数放到真实模型规模上是什么概念。一个 70B（700 亿）参数的模型，仅这部分就需要约 1,400GB 显存，而目前单块高端 GPU（比如 H100）的显存是 80GB 量级。远小于 70B 的模型，一块卡往往也放不下。这还没算上训练时的中间激活值，也就是前向传播过程中每一层的输出，反向传播要用它们来算梯度。这部分显存会同时随批量大小线性增长、随序列长度平方级增长，序列一长，激活值本身就可能超过参数和优化器状态的总和。

这就是为什么训练前沿模型必须把计算任务拆开，分布到成百上千块 GPU 上。首要原因是单块卡的显存物理上装不下，"算得更快"是次要考虑。

二、 四种并行方式在切什么

Hugging Face 的《Ultra-Scale Playbook》把训练大模型时用到的并行策略归纳为四类，它们切分的对象各不相同，因此可以叠加组合使用。

1. 数据并行（Data Parallelism, DP）

最直接的思路：把同一份完整的模型复制到每块 GPU 上，把一个大批次的训练数据切成小份，分别喂给不同的 GPU 各自算一遍前向和反向传播，算完之后把所有 GPU 算出的梯度做一次全体同步平均（这个操作叫 All-Reduce），再各自用平均后的梯度更新参数。真正的瓶颈是通信而非计算。GPU 数量越多，每一步都要做一次全体同步，同步的通信开销会随着 GPU 数量增加而变得越来越明显，尤其是跨物理节点（服务器）之间的通信，比同一节点内部通过 NVLink 高速互联的通信慢得多。Playbook 的实测数据显示，数据并行的效率在超过单节点约 8 块 GPU 后就会出现明显下降。

2. 张量并行（Tensor Parallelism, TP）

数据并行没有解决"模型本身放不下"的问题，因为每块卡上还是有一份完整模型。张量并行的做法是把模型内部单层的权重矩阵按行或按列切开，分别放到不同 GPU 上，每块卡只算这一层计算的一部分，算完后再把结果拼起来，这样单块卡真正只需要存模型参数的一部分。代价是：原本一层内部一次性就能算完的矩阵乘法，现在被拆成了几块 GPU 各算一部分再同步的过程，每一层都需要额外的通信，且这部分通信没办法和计算完全重叠，会变成暴露在外的开销。Playbook 的实测显示，张量并行度从 8 提高到 16，也就是从节点内部的 NVLink 通信跨越到节点间通信时，吞吐量会出现约 43% 的明显下降。

3. 流水线并行（Pipeline Parallelism, PP）

另一种切法是按层切：把模型的几十上百层，按顺序分成几段，每一段放到一块 GPU 上，数据像流水线一样依次流过各块卡。这样做的天然问题是"气泡"（bubble）。如果只有一份数据在流水线里跑，同一时刻只有一块 GPU 在真正工作，其余都在空等。解决办法是把一个大批次切成很多个"微批次"（micro-batch），让多个微批次在流水线里错峰重叠执行，尽量把空闲时间填满。即便如此，理论上仍然存在气泡率 r = (p−1)/m，p 是流水线段数，m 是微批次数量，段数越多、微批次数量不够多，浪费的比例就越高。Playbook 的实测里，流水线并行从单节点 8 卡扩展到跨节点 16 卡，吞吐量只下降约 14%，明显优于张量并行在同样跨节点场景下 43% 的下降。这也是为什么流水线并行更适合用在跨节点这一级别的切分。

4. 上下文并行 / 序列并行（Context / Sequence Parallelism）

前三种都是在切模型或数据批次，上下文并行切的是序列长度本身，把一条很长的输入序列按位置切成几段，分别放到不同 GPU 上处理。这是应对超长上下文（几万甚至几十万 token）训练时，激活值显存随序列长度平方级增长这个问题的主要手段。

三、 ZeRO：不切模型，但把优化器状态和梯度分摊出去

除了以上四种切分方式，Playbook 里还有一套常和数据并行搭配使用的显存优化技术，叫 ZeRO（Zero Redundancy Optimizer，微软提出）。它不切模型结构，问的是另一个问题：数据并行下每块卡都存了一份完整的优化器状态、梯度、参数，这里面有大量冗余，能不能让每块卡只存整体的一部分，需要用到别的部分时再临时去别的卡上取？

ZeRO 分三个递进的阶段。ZeRO-1 只对优化器状态做这种分片，ZeRO-2 在此基础上再对梯度分片，ZeRO-3 进一步连参数本身也分片。分片程度越深，单卡显存占用越低，但需要的临时通信（把分散在各卡上的分片重新收集起来）也越多。以 ZeRO-3 为例，一次训练步骤里，前向传播、反向传播、梯度归约分别都需要一次通信量约等于参数总量 Ψ 的操作，总通信量约为 3Ψ。这是用通信开销换取显存节省的一个典型例子，具体该用到哪个阶段，取决于集群里 GPU 数量、显存大小和网络带宽的具体组合。

实际训练一个前沿模型，往往会把数据并行、张量并行、流水线并行、上下文并行叠加组合使用，Playbook 称之为"多维并行"，并根据集群的物理拓扑结构（同节点内 NVLink 带宽远高于跨节点网络带宽）决定先在小范围内做哪种切分、再在大范围内做哪种切分。这正是"万卡集群训练工程"这个说法背后真正复杂的地方。没有一套放之四海皆准的最优配置，每一次超大规模训练，本质上都是针对具体硬件条件重新做一遍这道组合优化题。
