第六讲：并行训练策略的全景解构

从单卡内的算子融合，到跨机房上千张卡之间如何互相通信

主讲：Percy Liang / Tatsunori Hashimoto（斯坦福大学计算机系）
对应真实课程材料：Lecture 7 讲稿（literate Python 源码，含可运行的最小实现）

一、 为什么需要多卡：不只是"想训得更快"

这一讲开篇给出了两条独立的理由，说明为什么必须用多张 GPU 训练：第一，模型的优化器状态、梯度、激活值加起来放不进一张卡的显存（这是硬约束，不是"想不想"的问题）；第二，想用更多的总算力（FLOPs）把训练加速。这两条理由分别对应两类不同的并行策略，混在一起容易搞混。

讲义延续了上一讲"单卡内存层级"的思路，把它扩展到了跨设备的场景：单节点单卡内，最快的是 L1 缓存/共享内存，其次是 HBM 显存；单节点多卡之间，靠 NVLink/NVSwitch 连接；跨节点多卡之间，靠 InfiniBand 或以太网连接，离得越远，带宽越低、延迟越高。上一讲的主题是"减少单卡内的显存访问"（融合、分块），这一讲的主题是同一个思路的延伸："减少跨卡/跨机器之间的通信量"（通过复制或切分数据）。

讲义给出了几个真实的硬件带宽数字，很值得记住量级：单节点内 GPU 通过 PCIe（v7.0，16 通道）通信，带宽约 242 GB/s；同节点内通过 NVLink（以 B200 的 NVLink 5.0 为例）可达 1.8 TB/s（作为对比，片内 HBM 显存带宽约 8 TB/s）；跨节点通过 InfiniBand，带宽骤降到约 0.05 TB/s。真实数据中心的典型拓扑是：每个节点 8 张 GPU 通过 NVSwitch 互联，256 个节点组成一个"pod"通过 InfiniBand 互联，多个 pod 再通过以太网组成整个集群，像 GB200/GB300 NVL72 这样的新硬件，则是把 72 张 GPU 塞进同一个 NVLink 域，尽量扩大"通信很快"的范围。这个悬殊的带宽层级差异（HBM 比 InfiniBand 快上百倍），正是所有并行策略设计时要优先考虑的约束条件。

二、 集合通信操作：分布式训练的"基本词汇表"

理解各种并行策略之前，需要先认识几个反复出现的"集合通信操作"（collective operations）。这是从上世纪 80 年代并行计算文献里传下来的经典抽象，指定好一种通信模式（而不是自己手写点对点通信），交给底层库去做优化。设 rank 表示某张卡的编号，world_size 表示总卡数，几个核心操作是：

  • Broadcast（广播）：把 0 号卡上的数据原样复制给所有卡。典型用途：0 号卡加载初始 checkpoint，广播给其余所有卡。
  • Scatter / Gather（分发 / 收集）：Scatter 把 0 号卡上的一份数据切开，分别发给各卡；Gather 是反过来，把各卡上的数据收集回 0 号卡。
  • Reduce（规约）：把各卡上的数据收集到 0 号卡，同时做一次聚合运算（比如求和），例如各卡的数据是 $[0,1,2,3]$，Reduce-Sum 后 0 号卡得到 $6$。
  • All-gather：Gather 的"人人有份"版本，每张卡最后都拿到全部数据的完整拼接，而不只是 0 号卡。典型用途：每张卡只持有参数的一个分片，需要先 All-gather 出完整参数才能做前向传播。
  • Reduce-scatter：先做 Reduce（聚合），结果再按维度 Scatter 分发到各卡，每张卡只拿到聚合结果里属于自己的那一部分。典型用途：反向传播后，把各数据分片算出的梯度加总，但加总的结果依然分散存储在各卡上，不需要每张卡都存一份完整梯度。
  • All-reduce = Reduce-scatter + All-gather：先聚合再让每张卡都拿到完整的聚合结果。典型用途：反向传播后，把各卡上（基于不同数据分片算出的）梯度加总，并让每张卡都拿到同一份完整梯度，从而保证下一步更新后所有卡上的参数依然完全一致。把 All-reduce 拆解成"Reduce-scatter + All-gather"这两步，正是 ZeRO/FSDP 这类"显存节省型"数据并行技术的设计起点，因为拆开之后，你可以选择"聚合完之后要不要真的把完整结果攒回每张卡"，而不是被迫每次都攒一份完整副本。
  • All-to-all：最一般的形式，每张卡都要给每一张其他卡发送（不同的）数据。这是 MoE 路由的核心操作：每张卡上有一部分 token 和一部分专家，token 需要被路由到正确的专家所在的卡上，数据分布均衡时，All-to-all 的通信模式本质上就是一次"矩阵转置"。

三、 三种基础并行策略：切数据、切宽度、切深度

讲义用一个简化的多层感知机（MLP）模型，给出了三种并行策略各自的最小可运行实现（这里用 4 层线性层加 GELU 激活的玩具模型举例，因为讲义指出 MLP 正是 Transformer 里真正吃计算量的部分，这个简化例子对理解整体思路有代表性）：

数据并行（Data Parallelism）

每张卡持有完整的模型参数，但只分到一部分训练数据（比如总 batch size 128，4 张卡每张卡拿 32 条）。每张卡各自独立做前向和反向传播，算出各自基于本地数据的梯度。这一步各卡的 loss 数值是不同的，因为看到的数据不同。关键的一步只有一行代码：反向传播完成后，对每一个参数的梯度做一次 All-reduce（求平均），这样每张卡拿到的梯度就变得完全一致，用同样的梯度更新，也就保证了每张卡上的参数始终保持同步。这正是最经典的 DDP（Distributed Data Parallel）的核心机制，除了这一次 All-reduce，其余代码和单卡训练几乎完全一样。它的局限很直接：每张卡都要能装下完整的模型参数、梯度和优化器状态，模型一旦大到单卡装不下，纯数据并行就失效了（这也是后续课程要讲的 FSDP/ZeRO 要解决的问题：用 All-gather + Reduce-scatter 替代整份 All-reduce，把参数也分片存储）。

张量并行（Tensor Parallelism）

这次反过来：每张卡只拿到全部的训练数据，但只持有每一层参数矩阵的一部分（按输出维度切分成 world_size 份）。每张卡用自己那一小片参数对完整输入做矩阵乘法，得到一部分输出维度的激活值；要得到下一层需要的完整激活，必须做一次 All-gather，把各卡算出的局部激活拼接成完整的激活张量，再送进下一层重复这个过程。它的代价很直接：每一层都要做一次通信，对互联带宽的要求极高。这也是讲义特别强调"张量并行需要非常快的互联（比如 NVLink）"的原因：这种策略几乎只适合放在同一节点内、通过高速 NVLink 连接的几张卡之间，跨节点用张量并行通常会因为通信开销太大而得不偿失。

流水线并行（Pipeline Parallelism）

第三种策略沿着"深度"切分：每张卡只持有模型一部分连续的层（比如 4 层模型分给 2 张卡，每张卡各 2 层），数据像流水线一样依次流经各卡，0 号卡算完自己那部分层，把中间激活通过 dist.send 传给 1 号卡，1 号卡接收后（dist.recv）继续算剩下的层。这样做的通信量比张量并行小得多（只在层与层的"边界"通信，而不是每一层内部都通信），因此对互联速度的要求相对宽松，即便跨节点、用较慢的连接也能工作。但它有一个经典的效率陷阱：如果不做特殊处理，2 号卡在等待 1 号卡传数据过来之前只能空闲。这段空闲时间被称为"流水线气泡"（pipeline bubble）。讲义给出的缓解办法是把一个大 batch 切成多个"微批次"（micro-batch），让不同微批次在流水线的不同阶段同时流动，尽量把每张卡的空闲时间填满（讲义也坦诚指出：完整实现"通信与计算重叠"来彻底消除气泡，留作练习，这里给出的只是最基础的版本）。

四、 三种策略怎么选：没有免费的午餐

这三种策略在真实大规模训练中几乎总是组合使用，而不是二选一，业内常说的"3D 并行"就是数据、张量、流水线三种切分方式的组合叠加，外加处理 MoE 时还会再加一维"专家并行"。选择的核心依据始终是这一讲反复强调的那条主线：通信带宽的层级结构决定了切分策略的边界，张量并行通信最频繁（每层一次），只能放在 NVLink 覆盖的高速域内；流水线并行通信最稀疏（层边界一次），可以跨越较慢的连接；数据并行的通信量取决于模型总参数量，是三者中相对最容易跨节点扩展的一种。讲义总结的这条经验法则，会在下一讲讨论"给定算力预算，模型该多大、数据该多少"的 Scaling Laws 时，成为把理论最优配比落地成真实训练方案的关键约束。
