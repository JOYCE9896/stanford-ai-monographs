第六讲：AIOps与智能运维的自动化闭环

当一个云服务同时运行在几十万台机器上，出问题的时候人工排查已经来不及了

主讲：Matthew Johns（Microsoft）
对应真实背景：Microsoft Azure 的AIOps体系，包括异常检测服务 Azure Metrics Advisor 与微软研究院合作开发的 AiDice 算法

一、 IT运维在云计算规模下遇到的问题

传统IT运维靠人来盯着监控大盘，看到某个指标异常了就去排查原因。这套方式在系统规模不大的时候是可行的，但当一家公司的云基础设施横跨几十万台服务器、每秒产生海量的日志和监控指标时，靠人工盯屏幕已经不现实。AIOps（AI for IT Operations）指的是用机器学习和自动化技术接管这套监控和响应流程，让系统自己发现异常、定位原因，必要时自己动手修复，而不是每次都等人来处理。

二、 AIOps系统的三层结构

一套完整的AIOps系统通常分三层。第一层是数据采集层，从各种监控工具、云服务、应用程序里收集运行数据，包括系统指标、日志和调用链路追踪。第二层是AI分析层，用机器学习模型在这些数据里找规律、识别异常。第三层是自动化响应层，一旦确认了问题和根因，触发预先定义好的修复流程，比如重启某个出问题的服务、回滚一次有问题的部署。

这三层里最关键也最难的是第二层。系统每时每刻都在产生海量指标，其中大部分波动都是正常的业务波动，比如流量在白天和夜里本来就不一样。AIOps要做的是从这些正常波动里，把真正值得关注的异常信号挑出来，这类异常包括内存泄漏导致的持续性能下滑、流量模式的突变、配置漂移，或者某个服务的响应时间在悄悄劣化。如果模型对正常波动过于敏感，会产生大量无意义的告警，反而让运维团队疲于应付；如果模型不够敏感，又会漏掉真正的问题。

三、 微软在这个方向上的具体实践

微软的 Azure Metrics Advisor 是一套面向时间序列数据的AI异常检测服务，专门针对运维指标和业务关键指标（KPI）设计，它建立在微软认知服务（Cognitive Services）的基础上，用统计学和机器学习方法把真正有意义的异常从噪声里区分出来。微软研究院还和 Azure 团队联合开发了一套名为 AiDice 的异常检测算法，专门处理大规模、多维度的时间序列数据，这类数据的难点在于异常往往不是单个指标的孤立波动，而是多个相关指标同时出现某种协同变化模式，需要模型能够捕捉指标之间的关联性，而不是逐个指标独立判断。

在自动化响应这一层，实践中通常会把修复动作和预先写好的"运行手册"（Runbook）或无服务器函数（Serverless Function）绑定，系统检测到某类已知问题模式时，先尝试执行这些预定义的修复步骤，比如重启服务或回滚到上一个稳定版本，只有当自动修复无效或者问题模式是系统从未见过的新情况时，才会升级给人工工程师介入。

四、 AIOps和传统监控系统的本质区别

传统监控系统依赖人工设定的固定阈值，比如CPU使用率超过90%就告警。这种方式在系统行为相对稳定时够用，但现代云服务的正常运行状态本身就在不断变化，一个固定阈值要么在业务高峰期频繁误报，要么在业务低谷期又对真实异常反应迟钝。AIOps的核心价值在于，它的判断标准是从系统自身的历史行为模式里学出来的，能够随着系统状态的变化动态调整"什么算正常、什么算异常"的边界，这也是为什么这类系统需要用到机器学习，而不是简单的规则引擎就能解决。
